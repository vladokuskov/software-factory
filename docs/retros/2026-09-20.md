## 2. Patterns

Three tasks is a thin week, so the bar for "pattern" here is: the same thing on
all three, independently, with a worker or reviewer saying so in writing.

**A. The dataset is fragile (1 incident, but it took out 100% of the data).**
Not a pattern of behaviour, a structural gap: the retro's only input lives in
the product's tracked tree, where any revert, reset or checkout can rewrite
it. Locks, scope and current bindings are already treated as machine-local
state; the cycle log was the exception, and it is the one that matters.

**B. Under-specified input contract (3 of 3 tasks).** The criteria pinned exact
output strings, which worked: no format drift across three parallel agents.
They said nothing about no-input, surplus-input or malformed-input, so each
worker decided alone:

- #2 chose `args.join(' ')` for multi-word queries and usage on empty (PR #9
  body, "three points the spec left open").
- #3 chose to silently ignore extra operands on `rm`, "mirroring `list`". The
  intent reviewer raised it as important and the adversarial reviewer as
  minor; two reviewers converging on one unspecified choice is the clearest
  signal in the week. The worker's own spec feedback on PR #15: "for any
  mutating command the criteria should carry a checkable line such as 'extra
  arguments return usage'".
- #4 chose to ignore args and recorded it as a decision on the task.

**C. Tests that cannot fail (3 of 3 PRs, all caught by the adversarial reviewer,
never by a gate).**

- PR #9: the "formats matches like `list`" test asserted a hardcoded string,
  so the two commands could diverge with the test green.
- PR #15: a sabotaged `rm` that deleted `n1` on every miss passed all seven
  original tests; nothing checked the store after a failed delete.
- PR #16: the fixture had no count tie and insertion order matched the expected
  output, so deleting the sort passed all six tests.

Same class every time: a test that stays green with the behaviour removed. The
standard exists in the adversarial reviewer's prompt and nowhere a worker
reads. It cost an important finding on #16 and minor findings on the other two.

## 3. Changes on this branch

Three, matching the three patterns above.

**1. `cycles/` is ignored, and `cycle summary` distinguishes "missing" from
"empty".** `lib/init.sh` (both `init` and `link`) now writes `cycles/` into
`.factory/.gitignore`, so no product-side git operation can touch the log.
`lib/cycle.sh` returns a `warning` field when the directory is absent instead
of silent zeros. *Prevents:* the log being deleted by a revert, and a retro
misreading deletion as a quiet week. *Next week:* `factory cycle summary` rounds
equals the number of PRs that had a review comment, and no `warning` field.
Existing projects need `factory init` re-run (idempotent) or the one line added
by hand; the recovered entries for #2, #3, #4 were written back into
`factory-scratch/.factory/cycles/` as untracked files.

**2. Input contract in the task template and the epic checklist.**
`templates/task.md.tpl` gains an "Input contract" section (no input, surplus
input, malformed input, one line each, with the rule that a mutating operation
refuses rather than half-completes). `skills/epic/SKILL.md` lists it beside
acceptance criteria. *Prevents:* pattern B. *Next week:* zero review findings
whose fix is "define what happens with extra or missing input", and PR bodies
whose "decisions the spec left open" section is empty or absent.

**3. "Every test must be able to fail" in the worker prompt and the task
skill.** `agents/worker.md` step 4 and `skills/task/SKILL.md` step 4 tell the
worker to name, per criterion, the test that goes red when the behaviour is
removed or reversed, before opening the PR. *Prevents:* pattern C. *Next week:*
zero adversarial findings of the class "test passes with the behaviour
deleted". If they persist, the fix moves from prompt to gate (a mutation-test
step), which is more expensive, so try the prompt first.

## 4. Seen, not changed

- **`ultrareview` unavailable, 3 of 3 rounds, 0 findings ever.** A reviewer
  that never runs is broken, not redundant. Already documented as a known
  limitation. If it is still unavailable next week, remove it from
  `skills/review/SKILL.md` and `docs/FACTORY.md` rather than paying the
  attempt on every round.
- **`review-quality`: 0 critical, 0 important, 2 minor in 3 rounds.** Too few
  rounds to call redundant. Watch it. If a month passes with nothing above
  minor, remove it.
- **`EnterWorktree` failed for 2 of 3 workers** (subagent with pinned cwd),
  each rediscovering the `git worktree add` fallback, and the resulting branch
  names (`worktree-factory+3-rm-command`) do not match the `factory/<id>-<slug>`
  rule in `CLAUDE.md`. Costs time, not rounds. Candidate for next retro if it
  repeats.
- **Wave 2 started before wave 1 merged** (both #3 and #4 workers flagged it;
  PR #9 is still open). The plan's own rule, broken by the lead on the first
  epic. Harmless here because scopes were disjoint. One incident.
- **Epic #1's body says commands "register themselves in `src/registry.ts`",
  the plan says the opposite for wave 2.** Worker on #3 flagged it. One
  incident; the template could stop the epic body from carrying mechanics the
  plan owns, but not on one data point.
- **Task #23 has a malformed scope.** Filed by hand with a prose `Scope:` line,
  so the adapter parsed it into three entries containing backticks and
  parentheses. The scope hook will deny every write on that task. A harness
  defect: `factory task create` should reject scope entries that are not
  plausible paths. Not fixed here, three changes is the cap.
- **A direct push to `main` reached trunk with no task or review** and is
  what deleted the cycle log. Branch protection is the fix and it is a human
  decision.
